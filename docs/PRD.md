# 커피 주문 앱

## 1. 프로젝트 개요

### 1.1 프로젝트 명
커피주문 앱

### 1.2 프로젝트 목적
사용자가 커피 메뉴를 주문하고, 관리자가 주문을 관리할 수 있는 간단한 풀스택 웹 앱

### 1.3 개발 범위
- 주문하기 화면(메뉴 선택 및 장바구니 기능)
- 관리자 화면(재고 관리 및 주문 상태 관리)
- 데이터를 생성/조회/수정/삭제할 수 있는 기능

## 2. 기술 스택
- 프런트엔드: HTML, CSS, 리액트, 자바스크립트
- 백엔드: Node.js, Express
- 데이터베이스: PostgreSQL

## 3. 기본 사항
- 프런트엔드와 백엔드를 따로 개발
- 기본적인 웹 기술만 사용
- 학습 목적이므로 사용자 인증이나 결제 기능은 제외
- 메뉴는 커피 메뉴만 있음

# 주문하기 화면 PRD

## 1. 문서 개요

### 1.1 목적
첨부된 와이어프레임을 바탕으로 사용자가 커피 메뉴를 선택하고 옵션을 지정한 뒤, 장바구니에서 금액을 확인하고 주문하는 화면의 요구사항을 정의한다.

### 1.2 대상 사용자
- 커피 메뉴와 옵션을 선택해 주문하려는 사용자

### 1.3 범위
- 메뉴 목록과 메뉴별 옵션 표시
- 메뉴 옵션 선택 및 장바구니 담기
- 장바구니의 주문 내역과 총 금액 표시
- 주문 제출 및 결과 안내

관리자 화면의 메뉴·재고 관리와 주문 상태 관리, 결제, 회원가입 및 로그인은 이 화면의 범위에서 제외한다.

### 1.4 근거 및 범위 기준
- **발견 방법**: 사용자가 제공한 주문하기 화면 와이어프레임과 기존 프로젝트 개요를 검토했다.
- **검토 항목**: 와이어프레임 1개
- **대상**: 주문하기 화면 1개. 함께 제공된 관리자 화면은 이번 PRD의 대상이 아니다.

## 2. 사용자 시나리오 및 테스트

### 시나리오 1: 메뉴를 골라 장바구니에 담기 (우선순위 P1)
사용자는 메뉴와 원하는 옵션을 선택해 장바구니에 담고, 선택한 메뉴의 가격이 반영된 것을 확인한다.

**우선순위 근거**: 메뉴 선택과 장바구니 담기는 주문하기 화면의 핵심 가치다.

**독립 테스트**: 메뉴 하나를 선택하고 옵션을 적용해 담은 뒤 장바구니 항목과 금액을 확인한다.

**인수 시나리오**
1. **Given** 메뉴 목록이 표시되어 있을 때, **When** 사용자가 메뉴 카드의 옵션을 선택하고 `담기`를 누르면, **Then** 선택한 메뉴와 옵션이 장바구니에 표시되고 해당 가격이 반영된다.
2. **Given** 옵션이 추가 금액을 가진 메뉴일 때, **When** 사용자가 해당 옵션을 선택하면, **Then** 메뉴 가격에 옵션 금액이 더해진다.
3. **Given** 같은 메뉴와 같은 옵션 조합이 이미 장바구니에 있을 때, **When** 사용자가 해당 조합을 다시 담으면, **Then** 별도 중복 행을 만들지 않고 해당 항목의 수량이 증가한다.
4. **Given** 같은 메뉴라도 옵션 조합이 다를 때, **When** 사용자가 각 조합을 담으면, **Then** 서로 다른 장바구니 항목으로 구분된다.

### 시나리오 2: 주문 금액 확인하기 (우선순위 P1)
사용자는 장바구니에서 메뉴별 수량과 항목 금액, 주문 총액을 확인한다.

**우선순위 근거**: 제출 전에 주문 내용과 지불할 금액을 확인할 수 있어야 한다.

**독립 테스트**: 서로 다른 메뉴와 옵션 조합을 담고 각 항목 금액과 총액이 올바른지 확인한다.

**인수 시나리오**
1. **Given** 장바구니에 항목이 있을 때, **When** 화면이 표시되면, **Then** 각 항목의 메뉴명, 선택 옵션, 수량, 항목 금액과 전체 총액이 보인다.
2. **Given** 메뉴별 수량과 가격이 정해져 있을 때, **When** 장바구니 내용이 변경되면, **Then** 각 항목 금액은 해당 단가와 수량의 곱으로, 총액은 항목 금액의 합으로 표시된다.
3. **Given** 장바구니가 비어 있을 때, **When** 사용자가 주문 영역을 보면, **Then** 총액은 0원으로 표시되고 주문 제출은 진행할 수 없다.

### 시나리오 3: 주문 제출하기 (우선순위 P1)
사용자는 장바구니를 확인한 뒤 주문을 제출하고 처리 결과를 확인한다.

**우선순위 근거**: 주문 제출이 주문 여정의 완료 단계다.

**독립 테스트**: 항목을 담고 주문을 제출한 뒤 성공 안내를 확인한다.

**인수 시나리오**
1. **Given** 장바구니에 하나 이상의 항목이 있을 때, **When** 사용자가 `주문하기`를 누르면, **Then** 현재 주문 내용과 총액으로 주문이 제출된다.
2. **Given** 주문이 정상적으로 접수되었을 때, **When** 제출 처리가 끝나면, **Then** 주문 접수 결과를 사용자에게 알리고 장바구니를 비운다.
3. **Given** 주문 제출에 실패했을 때, **When** 실패 결과가 반환되면, **Then** 실패 사실을 안내하고 장바구니 내용은 유지한다.

## 3. 예외 및 경계 상황
- 메뉴 목록을 불러오지 못하거나 메뉴가 없으면 원인을 알 수 있는 안내를 표시하고, 존재하지 않는 메뉴로 주문할 수 없어야 한다.
- 주문 제출 중 오류가 발생해도 장바구니의 메뉴, 옵션, 수량이 보존되어야 한다.
- 장바구니가 비어 있거나 수량이 0 이하인 주문은 제출할 수 없어야 한다.
- 옵션 가격이 0원인 경우에도 옵션 선택 상태를 표시하고 금액을 정확하게 계산해야 한다.
- 가격은 원 단위로 표시하고, 모든 항목 금액과 총액은 동일한 계산 규칙을 사용해야 한다.

## 4. 요구사항

### 4.1 기능 요구사항
- **REQ-001**: 화면은 서비스 브랜드와 `주문하기`, `관리자` 내비게이션 항목을 표시하고 현재 `주문하기` 화면을 구분해 보여야 한다.
- **REQ-002**: 화면은 주문 가능한 커피 메뉴를 카드 형태로 보여주며, 각 카드에는 메뉴 이미지, 메뉴명, 기본 가격, 간단한 설명 및 옵션이 표시되어야 한다.
- **REQ-003**: 메뉴 옵션은 선택 여부와 추가 금액을 알 수 있어야 한다. 제공된 와이어프레임의 예시는 샷 추가(+500원), 시럽 추가(+0원)이다.
- **REQ-004**: 사용자가 옵션을 선택한 메뉴를 `담기`로 추가하면, 장바구니에 메뉴·옵션 조합과 수량이 반영되어야 한다.
- **REQ-005**: 동일한 메뉴·옵션 조합을 다시 담으면 해당 항목의 수량을 늘리고, 옵션 조합이 다르면 별도 항목으로 표시해야 한다.
- **REQ-006**: 장바구니는 항목별 메뉴명, 선택 옵션, 수량, 항목 금액 및 전체 총액을 표시해야 한다.
- **REQ-007**: 항목 금액은 `(기본 가격 + 선택 옵션 추가 금액) × 수량`으로 계산하고, 총액은 장바구니 항목 금액의 합으로 계산해야 한다.
- **REQ-008**: 장바구니가 비어 있을 때 주문 제출을 막고, 사용자가 현재 주문할 항목이 없음을 알 수 있게 해야 한다.
- **REQ-009**: 장바구니에 항목이 있을 때 사용자는 `주문하기`를 통해 주문을 제출할 수 있어야 한다.
- **REQ-010**: 주문 제출 결과를 성공 또는 실패로 명확히 안내해야 한다. 실패 시 장바구니 내용을 보존해야 한다.
- **REQ-011**: 주문 성공 후에는 접수 결과를 안내하고 장바구니를 초기화해야 한다.

### 4.2 비기능 요구사항
- **REQ-012**: 메뉴, 옵션, 수량, 가격 및 주문 동작은 텍스트와 조작 상태로 구분 가능해야 하며, 색상만으로 정보를 전달해서는 안 된다.
- **REQ-013**: 메뉴 추가 및 장바구니 금액 변경 결과는 사용자 조작 후 1초 이내에 화면에 반영되어야 한다.
- **REQ-014**: 일반적인 데스크톱 및 모바일 화면에서 메뉴와 장바구니의 주요 정보 및 주문 동작을 가로 스크롤 없이 확인할 수 있어야 한다.

## 5. 주요 데이터 개념
- **메뉴**: 주문 가능한 커피를 나타내며 메뉴명, 설명, 이미지, 기본 가격 및 이용 가능 여부를 포함한다.
- **메뉴 옵션**: 메뉴에 추가로 선택할 수 있는 항목으로, 옵션명과 추가 금액을 포함한다.
- **장바구니 항목**: 특정 메뉴와 옵션 조합의 주문 단위로, 수량과 계산된 항목 금액을 포함한다.
- **주문**: 제출 시점의 장바구니 항목들과 총액, 접수 결과를 묶어 나타낸다.

## 6. 성공 기준
- **SC-001**: 사용성 테스트 참여자의 90% 이상이 도움 없이 메뉴 선택, 장바구니 확인, 주문 제출을 완료한다.
- **SC-002**: 메뉴 하나를 선택해 장바구니에 담고 주문을 제출하는 기본 흐름을 테스트 참여자가 60초 이내에 완료한다.
- **SC-003**: 기본 가격, 옵션 추가 금액, 수량이 주어진 모든 테스트 사례에서 항목 금액과 총액이 기대값과 일치한다.
- **SC-004**: 메뉴 추가 또는 수량 변경 뒤 장바구니 내용과 총액이 1초 이내에 갱신된다.
- **SC-005**: 정상 주문 제출 성공·실패 테스트에서 결과 안내가 표시되고, 실패 시 장바구니 내용이 모두 보존된다.

## 7. 가정 및 결정 사항
- 와이어프레임에 보이는 메뉴명과 가격(아메리카노 ICE 4,000원, 아메리카노 HOT 4,000원, 카페라떼 5,000원)은 화면 예시이며, 실제 메뉴 데이터는 별도로 관리한다.
- 와이어프레임의 샷 추가(+500원)와 시럽 추가(+0원)는 옵션 표시 예시다. 메뉴별 실제 옵션 제공 여부와 가격은 메뉴 데이터에 따른다.
- 주문 제출은 주문 접수를 의미하며 결제는 포함하지 않는다. 로그인 없이 주문할 수 있다.
- 장바구니 수량은 같은 메뉴·옵션 조합을 반복해 담는 방식으로 증가한다. 와이어프레임에 수량 수정·항목 삭제 조작이 표현되어 있지 않아 해당 기능은 이번 범위에 포함하지 않는다.
- 주문 성공 후 장바구니를 비우고 접수 결과를 안내하는 동작은 주문 완료 흐름을 위한 기본 동작으로 가정한다.

# 관리자 화면 PRD

## 1. 문서 개요

### 1.1 목적
관리자가 주문 처리 현황과 커피 메뉴별 재고를 확인하고, 재고 수량을 조정하며, 접수 대기 주문을 처리할 수 있도록 요구사항을 정의한다.

### 1.2 대상 사용자
- 커피 주문 앱을 운영하며 재고와 주문을 관리하는 관리자

### 1.3 범위
- 관리자 화면 내비게이션 표시
- 전체 주문과 상태별 주문 수 요약
- 커피 메뉴별 현재 재고 확인 및 증감
- 주문 내역 확인 및 주문 접수

메뉴 정보·가격·옵션 자체의 등록 및 편집, 취소·환불, 결제, 사용자 인증은 이 화면 PRD의 범위에 포함하지 않는다.

### 1.4 근거 및 범위 기준
- **발견 방법**: 사용자가 제공한 관리자 화면 와이어프레임과 기존 프로젝트 개요를 검토했다.
- **검토 항목**: 관리자 화면 와이어프레임 1개
- **대상**: 관리자 화면 1개. 주문하기 화면의 요구사항은 앞선 PRD 내용을 유지한다.

## 2. 사용자 시나리오 및 테스트

### 시나리오 1: 주문 및 처리 현황 확인 (우선순위 P1)
관리자는 대시보드에서 전체 주문과 접수·제조 중·제조 완료 주문 건수를 빠르게 확인한다.

**우선순위 근거**: 관리자가 현재 처리해야 할 업무량을 파악하는 기본 정보다.

**독립 테스트**: 서로 다른 상태의 주문을 준비하고 대시보드의 합계와 상태별 건수가 실제 주문과 일치하는지 확인한다.

**인수 시나리오**
1. **Given** 주문이 등록되어 있을 때, **When** 관리자가 관리자 화면을 열면, **Then** 총 주문 수와 접수·제조 중·제조 완료 건수가 표시된다.
2. **Given** 주문의 상태가 변경되었을 때, **When** 화면의 주문 현황이 갱신되면, **Then** 해당 주문은 기존 상태의 건수에서 제외되고 새 상태의 건수에 반영된다.
3. **Given** 주문이 하나도 없을 때, **When** 관리자가 화면을 열면, **Then** 각 주문 건수는 0으로 표시된다.

### 시나리오 2: 재고 확인 및 조정 (우선순위 P1)
관리자는 메뉴별 재고를 확인하고 증감 버튼으로 수량을 조정한다.

**우선순위 근거**: 재고를 정확히 파악하고 조정할 수 있어야 주문 운영이 가능하다.

**독립 테스트**: 초기 수량을 확인한 뒤 증감 버튼을 눌러 표시 수량이 의도한 만큼 변경되는지 확인한다.

**인수 시나리오**
1. **Given** 메뉴별 재고가 등록되어 있을 때, **When** 관리자가 화면을 열면, **Then** 각 메뉴명과 현재 재고 수량이 보인다.
2. **Given** 메뉴 재고가 10개일 때, **When** 관리자가 `+`를 누르면, **Then** 해당 메뉴의 재고가 1개 증가해 11개로 표시된다.
3. **Given** 메뉴 재고가 10개일 때, **When** 관리자가 `-`를 누르면, **Then** 해당 메뉴의 재고가 1개 감소해 9개로 표시된다.
4. **Given** 메뉴 재고가 0개일 때, **When** 관리자가 `-`를 누르면, **Then** 재고는 0개 미만으로 감소하지 않는다.

### 시나리오 3: 주문 확인 및 접수 (우선순위 P1)
관리자는 주문 시각, 주문 메뉴와 수량, 주문 금액을 확인하고 접수 대기 주문을 접수한다.

**우선순위 근거**: 주문을 확인하고 처리 단계로 넘기는 것이 관리자 화면의 핵심 업무다.

**독립 테스트**: 접수 대기 주문을 표시한 후 접수 버튼을 눌러 성공 결과와 상태별 건수 변화를 확인한다.

**인수 시나리오**
1. **Given** 접수 대기 주문이 있을 때, **When** 관리자가 주문 현황을 보면, **Then** 각 주문의 주문 시각, 메뉴명, 수량, 금액과 `주문 접수` 동작이 표시된다.
2. **Given** 주문이 접수 대기 상태일 때, **When** 관리자가 `주문 접수`를 누르면, **Then** 주문은 접수 처리되고 이후 상태가 제조 중으로 변경된다.
3. **Given** 주문 접수 처리가 실패했을 때, **When** 실패 결과가 반환되면, **Then** 실패 사실을 안내하고 주문은 접수 대기 상태로 유지된다.
4. **Given** 접수 대기 주문이 없을 때, **When** 관리자가 주문 현황을 보면, **Then** 주문이 없음을 명확히 표시한다.

## 3. 예외 및 경계 상황
- 재고를 불러오거나 저장할 수 없으면 실패 사실을 안내하고, 저장되지 않은 수량 변경을 성공한 것처럼 표시하지 않아야 한다.
- 재고는 0개 미만이 될 수 없으며, 0개인 메뉴는 재고 부족 상태를 식별할 수 있어야 한다.
- 주문 목록을 불러오지 못하면 오류를 안내하고, 잘못되거나 오래된 주문 정보를 정상 상태처럼 표시하지 않아야 한다.
- 이미 접수 처리된 주문을 다시 접수할 수 없어야 한다.
- 주문 상태가 다른 관리자 또는 처리에 의해 먼저 변경된 경우, 최신 상태를 반영하고 중복 접수를 막아야 한다.

## 4. 요구사항

### 4.1 기능 요구사항
- **REQ-015**: 화면은 서비스 브랜드와 `주문하기`, `관리자` 내비게이션 항목을 표시하고 현재 `관리자` 화면을 구분해 보여야 한다.
- **REQ-016**: 대시보드는 전체 주문 수와 접수 대기, 제조 중, 제조 완료 상태별 주문 수를 표시해야 한다.
- **REQ-017**: 주문 수 요약은 현재 주문 내역 및 각 주문의 상태를 반영해야 한다.
- **REQ-018**: 재고 영역은 관리 대상 커피 메뉴 각각의 이름과 현재 재고 수량을 표시해야 한다.
- **REQ-019**: 관리자는 메뉴별 `+` 및 `-` 조작으로 재고를 1개씩 증가 또는 감소시킬 수 있어야 한다.
- **REQ-020**: 재고 수량은 0 미만이 될 수 없어야 하며, 변경 결과와 저장 실패를 명확히 표시해야 한다.
- **REQ-021**: 주문 현황은 주문별 접수 시각, 주문 메뉴 및 수량, 금액, 현재 상태를 확인할 수 있어야 한다.
- **REQ-022**: 접수 대기 주문에는 `주문 접수` 동작을 제공해야 한다.
- **REQ-023**: 주문 접수에 성공하면 해당 주문을 제조 중 상태로 변경하고 대시보드의 상태별 건수를 갱신해야 한다.
- **REQ-024**: 주문 접수에 실패하면 오류를 안내하고 주문 상태를 접수 대기로 유지해야 한다.
- **REQ-025**: 재고 또는 주문 데이터가 없을 때 빈 상태를 안내하고, 주문 수는 0으로 표시해야 한다.
- **REQ-026**: 화면은 재고 및 주문 데이터를 불러오거나 저장하는 중임을 사용자에게 알리고, 처리 중 중복 동작을 방지해야 한다.

### 4.2 비기능 요구사항
- **REQ-027**: 재고 수량, 주문 시각, 메뉴·수량, 금액과 주문 상태는 텍스트로 식별 가능해야 하며 색상만으로 의미를 전달해서는 안 된다.
- **REQ-028**: 재고 조정 및 주문 접수 결과는 처리 완료 후 1초 이내에 화면에 반영되어야 한다.
- **REQ-029**: 일반적인 데스크톱 및 모바일 화면에서 대시보드, 재고 조작, 주문 확인과 접수 동작을 가로 스크롤 없이 사용할 수 있어야 한다.

## 5. 주요 데이터 개념
- **메뉴 재고**: 커피 메뉴와 현재 판매 가능 수량을 나타낸다.
- **주문**: 주문 시각, 주문 항목, 메뉴별 수량, 금액과 현재 처리 상태를 포함한다.
- **주문 상태**: 주문 처리 진행 상황으로, 와이어프레임과 프로젝트 범위의 요약 기준에 따라 접수 대기, 제조 중, 제조 완료 상태를 구분한다.

## 6. 성공 기준
- **SC-006**: 관리자 화면에서 대시보드의 전체 및 상태별 주문 수가 실제 주문 내역과 모든 테스트 사례에서 일치한다.
- **SC-007**: 관리자는 메뉴별 재고 수량을 10초 이내에 확인하고, 증감 조작 결과를 확인할 수 있다.
- **SC-008**: 재고 증감이 100%의 테스트 사례에서 정확히 1개 단위로 반영되며, 재고가 음수가 되는 사례는 0건이어야 한다.
- **SC-009**: 관리자는 접수 대기 주문의 세부 정보를 확인해 30초 이내에 접수할 수 있다.
- **SC-010**: 주문 접수 성공·실패 테스트에서 화면의 주문 상태와 대시보드 건수가 실제 처리 결과와 일치한다.

## 7. 가정 및 결정 사항
- 프로젝트 개요에 따라 별도의 사용자 인증은 구현하지 않는 것으로 가정한다. 따라서 관리자 화면의 접근 제어는 이번 범위에 포함하지 않는다.
- 와이어프레임에 표시된 메뉴명과 재고 수량 10개는 예시이며, 실제 메뉴 및 재고 데이터는 별도로 관리한다.
- `+`와 `-`는 한 번 누를 때마다 재고를 1개씩 조정한다.
- 접수 대기 주문의 `주문 접수` 동작은 주문을 제조 중으로 전환한다. 제조 완료로 전환하는 별도 조작은 와이어프레임에 없으므로 이번 화면 범위에 포함하지 않는다.
- 주문 접수는 기존 주문의 상태 처리이며 결제나 주문 취소를 포함하지 않는다.
